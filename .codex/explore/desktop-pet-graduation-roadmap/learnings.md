# 经验沉淀

## [2026-03-27] 第 1 轮迭代

### 有效的做法
- 先通过代码阅读确认现成挂点，再谈解耦，能显著减少空泛讨论。
- 先从 `RunAction(...)`、`Main.Say(...)`、`IController.MoveWindows(...)` 这类现成入口切入，比先读完整个 GameCore 更有效。
- 把“身体层”“桥接层”“大脑”三层强制分开表述，有助于稳定后续所有决策。

### 无效的做法
- 一开始就讨论全面重构 VPet，会迅速把任务拉向高风险和高不确定性。
- 把“解耦”理解为“立刻拆所有内部逻辑”是不现实的。

### 可复用的策略
- 对于不了解 C# 的用户，优先沉淀“阶段目标 + 文件落点 + 验收方式”的实施文档，而不是只给抽象架构图。
- 先做内置 POC，再插件化收敛，是这类改造任务更稳的推进方式。

### 要避免的坑
- 不要在第一阶段直接修改存档和深层 Mode 逻辑。
- 不要把 Python 后端和 VPet 内部对象直接耦合。
- 不要忽略 `.codex` 目录的 ACL 问题，记录文件需要提权写入。

## [2026-03-27] 第 2 轮迭代

### 有效的做法
- 在主窗口 `GameLoaded()` 之后再启动桥接，比更早介入初始化链路更稳，因为这时 `Main`、插件和窗口控制器都已就绪。
- 让轮询器只在主窗口启动，可以避免多开场景下重复消费同一条后端事件。
- 第一阶段事件翻译只保留 `bubble.show` 和 `motion.play(idle|move)`，有助于把验证目标压到最小。

### 无效的做法
- 在第一阶段尝试把桥接直接做成完整插件 + 总线，会把“能不能跑通”问题和“架构够不够优雅”问题混在一起。
- 直接在后台线程调用 `RunAction(...)` 或 `Main.Say(...)` 不安全，WPF 调用还是要回到 `Dispatcher`。

### 可复用的策略
- 桥接类单独放到 `VPet-Simulator.Windows/AgentBridge/` 目录，先把实现边界收干净，后续收敛到插件时迁移成本更低。
- 用环境变量承载第一阶段的轮询地址和间隔，可以避免先引入新的配置系统。

### 要避免的坑
- 不要让轮询器在所有 `MainWindow` 实例都启动，否则多存档/多开场景会重复拉取事件。
- 不要把后端接口做成“一次返回整批复杂状态”，第一阶段维持“单条事件 / 204 无事件”更容易排查。
