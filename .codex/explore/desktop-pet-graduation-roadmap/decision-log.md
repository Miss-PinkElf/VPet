# 决策日志

## [2026-03-27] 决策：将 VPet 固定为身体层，而不是完整业务底座
- **背景**：当前需要在毕设节奏内快速验证“高桌宠感前端 + 外部 Python 大脑”路线。
- **选择**：保留 VPet 的窗口行为和动画表现，把行为决策外移给 Python。
- **原因**：VPet 最强的部分是桌宠感身体层，不是现有内部业务逻辑。
- **放弃的方案**：直接继续 Electron 前端主线、全面重构 VPet、整体切到 C# 新架构。
- **影响**：后续实现以“桥接”优先，而不是“深度解耦”优先。

## [2026-03-27] 决策：长期桥接方案优先使用 MainPlugin
- **背景**：需要尽量降低对主工程的侵入性，保留后续回收和切换能力。
- **选择**：把长期 AgentBridge 放在 `MainPlugin` 生命周期中。
- **原因**：插件层已有主程序支持，拿得到 `IMainWindow`、`Main` 和 `Core`，且耦合面比直接改 `MainWindow` 更小。
- **放弃的方案**：长期把桥接代码硬写在 `MainWindow` 中。
- **影响**：POC 可以临时内置，但验证通过后建议插件化收敛。

## [2026-03-27] 决策：第一阶段只做窄事件协议
- **背景**：当前用户不熟悉 C#，需要降低实现复杂度和验证成本。
- **选择**：第一版事件协议只覆盖 `bubble.show`、`motion.play`、`mode.switch`、`window.move`。
- **原因**：这几个事件已经能覆盖说话、待机、移动和最小状态表现。
- **放弃的方案**：一开始就设计完整双向事件总线或全面状态机协议。
- **影响**：第一版实现目标更窄，验证路径更短。

## [2026-03-27] 决策：第一阶段不直接操作存档和深层状态
- **背景**：直接修改 `Core.Save` 和存档逻辑风险高，且不属于路线验证的必要条件。
- **选择**：第一阶段只操作动作、说话和轻量窗口控制。
- **原因**：先证明桥存在，再考虑深入改造。
- **放弃的方案**：直接用 Python 控制 `GameSave`、`Mode`、物品和持久化逻辑。
- **影响**：当前实现边界更清晰，风险更低。
