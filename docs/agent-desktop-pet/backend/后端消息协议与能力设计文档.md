# 后端消息协议与能力设计文档

## 1. 文档目的

这份文档用于回答四件事：

- 现在的后端到底已经能做什么
- 现在已经定义并实际落地了哪些消息类型
- 这些消息数据结构分别有什么用
- 基于当前协议，前端理论上能被后端驱动成什么样

这份文档面向“复用当前设计”的场景，所以会同时参考：

- 需求与设计文档中的目标协议
- `backend-agent` 的实际 schema / API / service
- `VPet.Plugin.AgentBridge` 的实际桥接实现

也就是说，本文档不是只写理想设计，而是尽量以“当前仓库已经成立的事实”为准。

## 3. 当前系统结构

当前系统已经基本形成“三层结构”：

### 3.1 Brain

`backend-agent`

职责：

- 接收聊天请求
- 调用上游 OpenAI 兼容模型
- 维护最小记忆接口
- 生成高层桌宠事件
- 编排 sequence / scenario
- 接收 VPet 回传的状态

### 3.2 Bridge

`VPet.Plugin.AgentBridge`

职责：

- 从后端轮询拉取事件 `GET /vpet/events/next`
- 把高层事件翻译为 VPet 可执行动作
- 把当前身体状态回传给后端 `POST /vpet/state`

### 3.3 Body

`VPet`

职责：

- 气泡显示
- 动作播放
- graph / 表情播放
- 模式切换
- 窗口移动
- 当前显示状态输出

## 4. 现在的后端可以做什么

按“已经实际存在”的能力总结，当前后端可以做这些事。

### 4.1 聊天闭环

- 提供 `POST /api/chat`
- 接收用户输入和有限历史
- 组装 system prompt + memory recall + history
- 调用 OpenAI 兼容 `/v1/chat/completions`
- 返回 `{ reply, model }`

### 4.2 最小记忆闭环

- 已定义三类记忆分类：`working`、`event`、`semantic`
- 当前实际实现是 `InMemoryStore`
- 当前聊天链路实际写入的是 `working memory`
- 当前召回方式是非常轻量的字符串包含匹配

结论：

- “记忆接口层”已经有了
- “长期记忆能力”还只是最小占位实现

### 4.3 高层事件分发

- 后端有统一 `PetEvent` 协议
- 支持 SSE 推送 `GET /api/events`
- 也支持给 VPet 插件轮询的单条消费接口 `GET /vpet/events/next`
- 有 `EventBus` 负责发布 / 订阅 / 轮询队列

### 4.4 主动驱动 VPet 身体层

当前后端已经能主动发出这些高层行为事件：

- `bubble.show`
- `emotion.set`
- `motion.play`
- `mode.switch`
- `move.intent`
- `window.move`

其中第一阶段正式主协议已经明显收口到：

- `bubble.show`
- `emotion.set`
- `motion.play`
- `mode.switch`
- `window.move`

`move.intent` 还在 schema 和插件里保留，但已经属于 legacy 兼容能力。

### 4.5 Sequence / Scenario 编排

当前后端不只能发“单条事件”，还已经支持：

- 预设场景 `scenario`
- 自定义序列 `sequence`
- 步骤级 `delay_ms`
- 步骤级 `wait_for`
- 状态门控后的串行动作

当前支持的等待条件：

- `event_applied`
- `move_complete`
- `motion_complete`

这意味着当前后端已经不是简单聊天接口，而是一个最小“行为编排后端”。

### 4.6 状态回传与观察

当前后端可以接收并保存 VPet 回传的最新状态：

- 位置状态
- 缩放比
- 当前 display graph / animat
- 当前 mode / working state
- 气泡是否显示中
- 最近一次被消费的事件元数据

这使后端具备了“发事件 -> 看执行结果 -> 再决定下一步”的最小闭环能力。

### 4.7 联调与协议验证

当前后端还提供了开发联调能力：

- `GET /dev/control`
- `GET /dev/quick-test`
- `POST /api/dev/messages`
- `GET /api/dev/scenarios`
- `POST /api/dev/scenarios/{scenario_id}`
- `POST /api/dev/sequences`
- `GET /api/dev/state`

结论：

- 现在的后端既是聊天后端
- 也是身体层协议测试后端
- 也是最小行为编排后端

## 5. 当前消息体系总览

当前消息不是一种，而是五组。

### 5.1 聊天消息

用于用户和后端对话。

### 5.2 行为事件消息

用于后端驱动前端 / VPet 做动作、说话、移动、切模式。

### 5.3 Sequence / Scenario 消息

用于把多个行为事件编排成一段可控流程。

### 5.4 状态回传消息

用于前端 / VPet 向后端报告当前身体状态。

### 5.5 记忆数据结构

用于后端内部记忆抽象，不直接面向 VPet，但会影响聊天与行为策略。

## 6. 消息类型设计明细

## 6.1 聊天消息

### `ChatMessage`

```json
{
  "role": "user",
  "content": "今天有点累。"
}
```

字段：

- `role`: `system | user | assistant`
- `content`: 文本内容

用途：

- 表示单条对话消息
- 用于 `history`
- 也用于后端发给上游 LLM 的 prompt message

### `ChatRequest`

```json
{
  "message": "今天有点累。",
  "history": [
    { "role": "assistant", "content": "怎么了？" }
  ]
}
```

字段：

- `message`: 当前用户输入
- `history`: 最近历史消息列表

用途：

- 前端调用 `POST /api/chat` 的请求体
- 后端用它构建 prompt

### `ChatResponse`

```json
{
  "reply": "那你先喘口气，我陪你理一下。",
  "model": "gpt-5.4"
}
```

字段：

- `reply`: 回复文本
- `model`: 实际使用的模型名

用途：

- 返回给前端显示聊天结果
- 也方便调试当前模型来源

## 6.2 基础事件公共结构

所有行为事件都继承同一组公共字段。

### `BasePetEvent`

```json
{
  "source": "backend",
  "event_id": "dev-control-a1b2c3d4e5f6",
  "sequence_name": "think-speak-move",
  "step_index": 2
}
```

字段：

- `source`: 事件来源
- `event_id`: 事件唯一标识
- `sequence_name`: 所属序列名
- `step_index`: 所属序列步骤索引

用途：

- 做链路追踪
- 做 sequence 步骤和 VPet 实际消费之间的对应
- 避免后端只靠 `last_event_type` 猜测当前执行到了哪一步

设计判断：

- `event_id` 现在非常重要，已经不是可有可无字段
- 对单事件也建议带上
- 对 sequence 更建议固定带全

## 6.3 当前正式行为事件

### `bubble.show`

```json
{
  "type": "bubble.show",
  "text": "我先想一下这件事。",
  "duration_ms": 4000,
  "motion": "thinking",
  "expression": "thinking",
  "graph": "think"
}
```

字段：

- `type = bubble.show`
- `text`
- `duration_ms`
- `motion` 可选
- `expression` 可选
- `graph` 可选

用途：

- 让桌宠显示说话气泡
- 可在说话时附带有限动作 / 表情 / graph

当前实际能力：

- 纯文本说话
- `touch_head / touch_body / pinch / thinking` 这类 motion 已做了更贴近 VPet 原生的说话编排
- `graph` 优先级高于 `expression`

### `emotion.set`

```json
{
  "type": "emotion.set",
  "emotion": "thinking",
  "graph": "think"
}
```

字段：

- `type = emotion.set`
- `emotion`
- `graph` 可选

用途：

- 切换当前表情 / graph

当前实际映射较窄：

- `think` -> `think`
- `thinking` -> `think`
- `pinch` -> `pinch`
- `shy` -> `pinch`

设计结论：

- 当前它更像“有限 graph 切换”
- 还不是完整情绪系统

### `motion.play`

```json
{
  "type": "motion.play",
  "motion": "touch_head",
  "priority": 55
}
```

字段：

- `type = motion.play`
- `motion`
- `priority`

用途：

- 触发单独动作

当前已确认稳定动作：

- `idle`
- `move`
- `normal`
- `touch_head`
- `touch_body`
- `sleep`
- `raised`
- `state_one`
- `pinch`
- `thinking`

### `mode.switch`

```json
{
  "type": "mode.switch",
  "mode": "thinking"
}
```

字段：

- `type = mode.switch`
- `mode`

用途：

- 切换高层模式态

当前已确认模式：

- `thinking`
- `normal`

设计结论：

- 当前 `mode` 还不是复杂状态机
- 更像两个高层视觉/行为模式入口

### `window.move`

```json
{
  "type": "window.move",
  "dx": 120,
  "dy": -20,
  "style": "smart"
}
```

字段：

- `type = window.move`
- `dx`
- `dy`
- `style`

用途：

- 显式窗口位移

当前风格：

- `smart`
- `smooth` / `walk`
- `snap` / `teleport`

当前语义：

- `smart` 会按位移距离自动选择平滑走位或直接跳位
- 这是第一阶段唯一正式移动协议

### `move.intent`

```json
{
  "type": "move.intent",
  "intent": "dock_right"
}
```

用途：

- 旧的高层移动意图协议

当前状态：

- 仍存在于 schema 和插件
- 但已经不是正式主协议
- 当前只保留最薄兼容

仅剩稳定 intent：

- `dock_left`
- `dock_right`
- `dock_top`
- `dock_bottom`

## 6.4 开发联调消息

### `DevEventRequest`

这是联调页发单事件时的请求结构。

特点：

- 它是“超集表单结构”
- 把所有事件可能用到的字段放在一个请求里
- 再由 `BehaviorPolicyEngine.build_manual_event()` 组装成正式 `PetEvent`

用途：

- 开发页手动发事件
- 统一参数校验
- 生成 `event_id`

### `DevEventResponse`

```json
{
  "status": "ok",
  "event": {
    "type": "motion.play",
    "motion": "touch_head",
    "priority": 55,
    "source": "dev-control",
    "event_id": "dev-control-123456789abc"
  }
}
```

用途：

- 返回真正被接受和发布的正式事件

## 6.5 Sequence / Scenario 消息

### `DevSequenceStepRequest`

```json
{
  "delay_ms": 0,
  "event": {
    "type": "window.move",
    "dx": 80,
    "dy": -20,
    "style": "smart"
  },
  "wait_for": "move_complete",
  "wait_timeout_ms": 5000,
  "settle_ms": 120
}
```

字段：

- `delay_ms`: 该步执行前等待多久
- `event`: 本步正式事件
- `wait_for`: 要等什么完成
- `wait_timeout_ms`: 最长等待时间
- `settle_ms`: 完成后再额外稳定多久

用途：

- 描述 sequence 的一步

### `DevSequenceRequest`

```json
{
  "name": "think-speak-move-touch-speak-recover",
  "source": "dev-sequence",
  "steps": []
}
```

用途：

- 触发自定义 sequence

### `DevSequenceDispatchResponse`

```json
{
  "status": "accepted",
  "sequence_name": "think-speak-move-touch-speak-recover",
  "step_count": 6,
  "source": "dev-sequence"
}
```

用途：

- 告知 sequence 已被后台接受并开始异步执行

### `DevScenarioSummary` / `DevScenarioListResponse`

用途：

- 返回预设场景目录
- 给联调页列出可直接点的 story / demo

当前这组结构的意义很大：

- 后端已经从“发单事件”升级到“发一段动作脚本”
- 以后前端不一定要自己写 demo 逻辑
- 后端可以直接编排一个桌宠演出流程

## 6.6 状态回传消息

### `VPetStateSnapshot`

```json
{
  "source": "vpet-plugin",
  "timestamp": "2026-03-29T10:00:00Z",
  "left": 320,
  "top": 140,
  "right": 980,
  "bottom": 620,
  "zoom_ratio": 1.0,
  "display_name": "think",
  "display_type": "B_Loop",
  "display_animat": "B_Loop",
  "mode": "Nomal",
  "working_state": "Free",
  "work_name": null,
  "work_type": null,
  "bubble_visible": true,
  "last_event_type": "bubble.show",
  "last_event_id": "dev-sequence-abc123",
  "last_sequence_name": "think-speak-move-touch-speak-recover",
  "last_step_index": 1,
  "last_event_at": "2026-03-29T10:00:01Z"
}
```

字段作用：

- `left / top / right / bottom`: 逻辑位置边界
- `zoom_ratio`: 当前缩放比
- `display_name / display_type / display_animat`: 当前显示 graph 和动画阶段
- `mode / working_state / work_name / work_type`: 当前 VPet 工作态
- `bubble_visible`: 气泡是否还在
- `last_event_type`: 最近消费的事件类型
- `last_event_id`: 最近消费的事件 ID
- `last_sequence_name`: 最近消费事件所属 sequence
- `last_step_index`: 最近消费的是 sequence 第几步
- `last_event_at`: 最近消费事件的时间

用途：

- 给后端看“身体当前是什么状态”
- 给 sequence 门控提供事实依据
- 给调试页提供观测面板

### `VPetStateResponse`

```json
{
  "status": "ok",
  "state": {}
}
```

用途：

- 统一包装状态查询与状态更新返回值

## 6.7 记忆数据结构

### `MemoryRecord`

```json
{
  "category": "working",
  "content": "用户说今天很累。"
}
```

当前分类：

- `working`
- `event`
- `semantic`

用途：

- 作为记忆写入的统一结构

### `MemoryRecallItem`

```json
{
  "content": "用户前几天也提到过加班。",
  "category": "working"
}
```

用途：

- 作为召回结果返回给聊天编排器

设计结论：

- 分类已经按长期方向留好了
- 但当前后端真正稳定写入和召回的仍然偏 `working`

## 7. 基于当前协议，前端现在能做成什么样

这里分成两层看。

## 7.1 当前已经能稳定做的

如果把 VPet 当“身体层”，当前前端已经可以被后端驱动出以下表现。

### 说话型桌宠

- 后端发 `bubble.show`
- VPet 显示气泡
- 可以叠加有限 graph / expression

这已经足够支撑：

- 基础陪聊
- 提醒
- 轻量主动提示
- 答辩演示里的“桌宠会说话”

### 动作型桌宠

- 后端发 `motion.play`
- VPet 播放摸头、摸身、思考、睡觉、回归 normal 等动作

这已经足够支撑：

- 交互反馈
- 回复时附动作
- 演示中的动作切换

### 模式型桌宠

- 后端发 `mode.switch(thinking|normal)`
- VPet 进入思考态或回到正常态

这已经足够支撑：

- “思考中”
- “恢复待机”
- 回复前的短暂停顿感

### 位移型桌宠

- 后端发 `window.move(dx, dy, style)`
- VPet 按显式位移移动窗口

这已经足够支撑：

- 靠近一点
- 挪开一点
- 脚本演示中的走位
- 长距离直接跳位

### 编排型桌宠

- 后端发 sequence
- 按步骤执行“思考 -> 说话 -> 移动 -> 动作 -> 恢复”

这已经足够支撑：

- 小型剧情演出
- 答辩标准 demo
- 行为脚本化验证

## 7.2 理论上已经具备协议基础、前端可以继续做的

虽然当前还没完全产品化，但协议方向已经允许前端往这些能力扩。

### 更完整的 Pet Controller

前端可以做统一控制层，负责：

- 事件去重
- 冲突仲裁
- 动作队列
- 用户拖拽与后端位移冲突处理
- 模式优先级管理

### 更丰富的情绪系统

当前 `emotion.set` 还是窄映射，但协议上已经预留：

- 语义 emotion
- graph 直指

后续只要前端补更多 graph 白名单，就能扩成：

- 开心
- 生气
- 无语
- 害羞
- 疲惫
- 惊讶

### 更强的行为脚本系统

当前 sequence 已经支持：

- delay
- wait_for
- settle
- step metadata

所以理论上前端可以承接：

- 更长剧情脚本
- 提醒脚本
- 欢迎脚本
- 睡眠 / 唤醒脚本
- 连续多个相同事件类型的稳定编排

### 更强的主动陪伴

只要后端行为策略再补齐，当前协议已经足够承接：

- 看见用户加班时提醒休息
- 在不同时间段切换桌宠状态
- 用动作 + 气泡表达陪伴感
- 根据上下文发起轻量主动互动

### 更换身体层实现

当前协议本质上传的是“高层事件”，不是底层每帧命令。

因此理论上未来可以把身体层替换成：

- Electron + Live2D
- Unity 壳
- 其他桌宠前端

只要新的身体层继续支持这组高层事件和状态回传即可。

## 8. 当前设计的核心原则

当前后端设计已经体现出几个明确原则。

### 8.1 后端负责“为什么做、做什么”

例如：

- 要不要说话
- 说什么
- 切什么模式
- 播什么动作
- 要不要位移

### 8.2 前端 / 身体层负责“怎么做、现在能不能做”

例如：

- 具体怎么播动画
- 当前拖拽中要不要拒绝位移
- graph 是否存在
- 动作冲突如何处理

### 8.3 传高层事件，不传每帧渲染命令

这保证了：

- 协议稳定
- 身体层可替换
- 后端不需要耦合具体渲染实现

### 8.4 用状态回传闭环，而不是只靠盲发

这也是当前设计和“纯联调页脚本”最大的区别。

现在已经形成：

- 发事件
- 身体层执行
- 身体层回传状态
- 后端根据状态判断下一步

## 9. 当前限制与不足

为了复用这套设计，限制也需要写清楚。

### 9.1 情绪系统还很窄

- `emotion.set` 还不是完整情绪层
- 当前更接近少量 graph 映射

### 9.2 记忆系统还是最小占位

- 当前没有真正长期持久化
- 没有 relationship memory
- 没有复杂 recall 策略

### 9.3 `move.intent` 不应继续作为主协议

- 它太虚
- 不利于稳定落地
- 正式调用应尽量改用 `window.move`

### 9.4 sequence 完成门控还不是全覆盖

当前相对可靠的是：

- `event_applied`
- `move_complete`
- `motion_complete`

但还不能宣称：

- 所有气泡生命周期都能精确门控
- 所有 graph 生命周期都能精确门控

### 9.5 当前更多是“协议稳定化阶段”，不是最终产品协议

也就是说：

- 核心骨架已经对了
- 但很多语义值仍需要继续白名单化和产品化

## 10. 复用建议

如果你要复用当前设计，建议直接保留下面这些结构。

### 10.1 保留 `BasePetEvent`

至少保留：

- `source`
- `event_id`
- `sequence_name`
- `step_index`

这是后续做追踪、日志、调试、sequence 门控的基础。

### 10.2 正式事件保持窄而稳定

第一阶段建议继续把正式事件收口在：

- `bubble.show`
- `emotion.set`
- `motion.play`
- `mode.switch`
- `window.move`

### 10.3 状态回传不要删 trace 字段

至少保留：

- `last_event_type`
- `last_event_id`
- `last_sequence_name`
- `last_step_index`
- `last_event_at`

这些字段对“后端知道前端到底执行到了哪里”很关键。

### 10.4 前端尽量做统一控制层

不建议把事件处理散落到各个组件。

建议继续采用：

- 一个 `Pet Controller`
- 一个动作 / 模式 / 位移仲裁层
- 一个状态快照上报层

### 10.5 聊天协议和行为协议分开

建议保持两条线：

- 聊天接口负责“语言内容”
- 行为事件负责“身体表现”

不要把动作、模式、位移全部硬塞进聊天接口返回值里。

## 11. 一句话结论

当前后端已经不是“只能聊天”的后端了。

它现在已经具备：

- 最小聊天能力
- 最小记忆接口
- 高层桌宠事件协议
- VPet 身体层桥接
- sequence/scenario 编排
- 状态回传闭环

从设计阶段来看，当前最值得复用的不是某一个接口，而是这套模式：

**后端做大脑与行为编排，前端做身体与执行仲裁，双方通过高层事件协议和状态回传闭环协作。**
