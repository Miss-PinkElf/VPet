# 通用前后端消息数据结构协议

## 1. 文档目标

这份文档不再围绕 `VPet` 本身展开，而是把当前项目里已经验证过的一组消息结构抽出来，整理成一个可迁移到其他项目的通用协议。

适用场景：

- 后端负责决策
- 前端负责表现和执行
- 后端需要主动给前端发消息
- 前端需要把执行状态回传给后端
- 需要支持单事件和多步骤编排

一句话总结：

**这是一套“后端发高层行为事件，前端回传执行状态”的通用消息数据结构。**

## 2. 设计原则

这套协议建议长期保持以下原则：

- 传高层事件，不传每帧渲染命令
- 数据结构独立于具体传输方式
- 同一套 payload 可跑在 HTTP、SSE、WebSocket、IPC、消息队列上
- 前端负责执行细节，后端负责意图和编排
- 每条事件尽量可追踪、可关联、可调试

## 3. 协议分层

建议把消息拆成五层。

### 3.1 聊天层

用于文本对话和 LLM 交互。

### 3.2 记忆层

用于后端内部记忆写入和召回。

### 3.3 行为事件层

用于后端主动驱动前端表现。

### 3.4 编排层

用于把多个行为事件串成 sequence / scenario。

### 3.5 状态回传层

用于前端把执行结果回传给后端。

## 4. 传输建议

这套协议不绑定某种传输方式。

推荐映射：

- 请求型接口：HTTP
- 服务端主动推送：SSE / WebSocket
- 本地桌面进程通信：IPC / Named Pipe / 本地 HTTP
- 轮询式前端：`GET next-event`

也就是说，协议的重点是消息体，不是接口形式。

## 5. 通用基础结构

## 5.1 聊天消息

### `ChatMessage`

```ts
type ChatRole = 'system' | 'user' | 'assistant'

interface ChatMessage {
  role: ChatRole
  content: string
}
```

作用：

- 表示一条对话消息
- 用于历史消息
- 用于拼接 LLM prompt

示例：

```json
{
  "role": "user",
  "content": "今天有点累。"
}
```

### `ChatRequest`

```ts
interface ChatRequest {
  message: string
  history: ChatMessage[]
}
```

作用：

- 前端发起聊天请求
- 后端据此构建对话上下文

示例：

```json
{
  "message": "今天有点累。",
  "history": [
    {
      "role": "assistant",
      "content": "怎么了？"
    }
  ]
}
```

### `ChatResponse`

```ts
interface ChatResponse {
  reply: string
  model: string
}
```

作用：

- 返回给前端的最终文本回复
- 标记实际使用的模型

示例：

```json
{
  "reply": "那你先歇一会儿，我陪你。",
  "model": "gpt-5.4"
}
```

## 5.2 记忆结构

### `MemoryRecord`

```ts
type MemoryCategory = 'working' | 'event' | 'semantic'

interface MemoryRecord {
  category: MemoryCategory
  content: string
}
```

作用：

- 统一记忆写入格式
- 后续可以挂到数据库、向量库、图谱库、文件系统

建议含义：

- `working`: 当前近期上下文
- `event`: 发生过的事件
- `semantic`: 稳定偏好、认知、习惯

### `MemoryRecallItem`

```ts
interface MemoryRecallItem {
  content: string
  category: string
}
```

作用：

- 统一记忆召回结果格式
- 供后端编排器注入聊天或行为策略

## 5.3 行为事件公共元数据

这组字段建议所有前端行为事件都带。

### `BaseEventMeta`

```ts
interface BaseEventMeta {
  source?: string
  event_id?: string
  sequence_name?: string
  step_index?: number
}
```

字段含义：

- `source`: 事件来源，例如 `backend`、`scheduler`、`dev-control`
- `event_id`: 单条事件唯一 ID
- `sequence_name`: 该事件属于哪条 sequence
- `step_index`: 该事件是 sequence 的第几步

作用：

- 方便日志追踪
- 方便前后端对齐同一条事件
- 方便在重复事件类型下判断到底消费了哪一步

建议：

- 正式环境也保留 `event_id`
- sequence 中固定带 `event_id + sequence_name + step_index`

## 6. 通用行为事件

这组事件名称已经在当前项目中验证过，建议直接复用。

## 6.1 `bubble.show`

表示“显示一段气泡 / 文本表现”。

```ts
interface BubbleShowEvent extends BaseEventMeta {
  type: 'bubble.show'
  text: string
  duration_ms?: number
  motion?: string
  expression?: string
  graph?: string
}
```

字段作用：

- `text`: 要展示的文字
- `duration_ms`: 展示多久
- `motion`: 说话时附带的动作语义
- `expression`: 说话时附带的表情语义
- `graph`: 前端直接识别的具体视觉资源名

前端能做什么：

- 显示对话气泡
- 显示 toast / speech bubble / caption
- 在显示文本时附带表情和动作

适合场景：

- 主动提示
- 聊天回复
- 状态提醒
- 小剧情脚本里的台词

示例：

```json
{
  "type": "bubble.show",
  "text": "你已经连续工作两小时了。",
  "duration_ms": 5000,
  "expression": "thinking"
}
```

## 6.2 `emotion.set`

表示“切换当前情绪 / 表情态”。

```ts
interface EmotionSetEvent extends BaseEventMeta {
  type: 'emotion.set'
  emotion: string
  graph?: string
}
```

字段作用：

- `emotion`: 高层语义值
- `graph`: 前端可直接使用的具体资源名

前端能做什么：

- 切换 Live2D 表情
- 切换 2D/3D 模型情绪参数
- 切换头像 / 状态图 / graph

适合场景：

- 思考态
- 害羞态
- 平静态
- 惊讶态

示例：

```json
{
  "type": "emotion.set",
  "emotion": "thinking",
  "graph": "think"
}
```

## 6.3 `motion.play`

表示“播放一个动作”。

```ts
interface MotionPlayEvent extends BaseEventMeta {
  type: 'motion.play'
  motion: string
  priority?: number
}
```

字段作用：

- `motion`: 动作语义名
- `priority`: 优先级，供前端做冲突仲裁

前端能做什么：

- 播放动作
- 播放姿态切换
- 触发一次性表现

适合场景：

- 摸头
- 招手
- 点头
- 睡觉
- 抬头
- 思考

示例：

```json
{
  "type": "motion.play",
  "motion": "touch_head",
  "priority": 60
}
```

## 6.4 `mode.switch`

表示“切到一个高层模式”。

```ts
interface ModeSwitchEvent extends BaseEventMeta {
  type: 'mode.switch'
  mode: string
}
```

字段作用：

- `mode`: 当前高层模式名

前端能做什么：

- 切到思考态
- 切到正常态
- 切到安静态
- 切到提醒态
- 切到陪伴态

适合场景：

- 行为模式切换
- UI 状态切换
- 一组默认动作/表情组合切换

示例：

```json
{
  "type": "mode.switch",
  "mode": "thinking"
}
```

## 6.5 `window.move`

表示“让前端实体产生明确位移”。

```ts
interface WindowMoveEvent extends BaseEventMeta {
  type: 'window.move'
  dx?: number
  dy?: number
  style?: string
}
```

字段作用：

- `dx`: x 方向位移
- `dy`: y 方向位移
- `style`: 位移风格

前端能做什么：

- 窗口移动
- 角色位置移动
- 元素容器平移
- 角色在某个空间中走位

适合场景：

- 靠近一点
- 挪开一点
- 演示脚本
- 剧情脚本

示例：

```json
{
  "type": "window.move",
  "dx": 120,
  "dy": -20,
  "style": "smart"
}
```

## 6.6 `move.intent`

这是一个 legacy 事件，表示“高层移动意图”。

```ts
interface MoveIntentEvent extends BaseEventMeta {
  type: 'move.intent'
  intent: string
}
```

作用：

- 用抽象语义表达位移

典型值：

- `dock_left`
- `dock_right`
- `dock_top`
- `dock_bottom`

建议：

- 新项目优先用 `window.move`
- `move.intent` 只在你真的需要“前端自己推导位移”时保留

## 6.7 统一事件联合类型

```ts
type FrontendBehaviorEvent =
  | BubbleShowEvent
  | EmotionSetEvent
  | MotionPlayEvent
  | ModeSwitchEvent
  | WindowMoveEvent
  | MoveIntentEvent
```

## 7. 开发联调结构

这组结构主要解决“调试时不想手写多套表单”的问题。

## 7.1 `DevEventRequest`

```ts
interface DevEventRequest {
  type: 'bubble.show' | 'emotion.set' | 'motion.play' | 'mode.switch' | 'move.intent' | 'window.move'
  text?: string
  duration_ms?: number
  emotion?: string
  motion?: string
  expression?: string
  graph?: string
  priority?: number
  mode?: string
  intent?: string
  dx?: number
  dy?: number
  style?: string
}
```

作用：

- 联调页表单结构
- 统一输入参数
- 便于转成正式事件

### `DevEventResponse`

```ts
interface DevEventResponse {
  status: 'ok'
  event: FrontendBehaviorEvent
}
```

作用：

- 返回已经被后端校验并转换完成的正式事件

## 8. 编排结构

如果你的另一个项目也要支持后端编排前端行为，建议直接复用这组结构。

## 8.1 `DevSequenceStepRequest`

```ts
type WaitForType = 'event_applied' | 'move_complete' | 'motion_complete'

interface DevSequenceStepRequest {
  delay_ms?: number
  event: DevEventRequest
  wait_for?: WaitForType
  wait_timeout_ms?: number
  settle_ms?: number
}
```

字段作用：

- `delay_ms`: 该步执行前等待
- `event`: 当前要发的事件
- `wait_for`: 等待某种完成条件
- `wait_timeout_ms`: 等多久算超时
- `settle_ms`: 完成后额外稳定一下

这组字段非常通用，因为它不依赖具体前端技术栈。

## 8.2 `DevSequenceRequest`

```ts
interface DevSequenceRequest {
  name?: string
  source?: string
  steps: DevSequenceStepRequest[]
}
```

作用：

- 描述一段完整前端行为流程

示例：

```json
{
  "name": "think-speak-move-recover",
  "source": "backend",
  "steps": [
    {
      "event": {
        "type": "mode.switch",
        "mode": "thinking"
      },
      "wait_for": "event_applied"
    },
    {
      "event": {
        "type": "bubble.show",
        "text": "我先想一下。",
        "duration_ms": 4000
      },
      "wait_for": "event_applied"
    },
    {
      "event": {
        "type": "window.move",
        "dx": 80,
        "dy": 0,
        "style": "smart"
      },
      "wait_for": "move_complete",
      "settle_ms": 120
    },
    {
      "event": {
        "type": "mode.switch",
        "mode": "normal"
      }
    }
  ]
}
```

## 8.3 `DevSequenceDispatchResponse`

```ts
interface DevSequenceDispatchResponse {
  status: 'accepted'
  sequence_name: string
  step_count: number
  source: string
}
```

作用：

- 返回“sequence 已接受并开始执行”

## 8.4 `Scenario`

如果另一个项目也会有预设脚本，建议保留：

```ts
interface ScenarioSummary {
  scenario_id: string
  title: string
  description: string
  step_count: number
}

interface ScenarioListResponse {
  status: 'ok'
  scenarios: ScenarioSummary[]
}
```

作用：

- 让前端或联调页知道有哪些可直接触发的预设演示

## 9. 状态回传结构

当前项目名叫 `VPetStateSnapshot`，但如果你要迁移到别的项目，建议把它抽象成更通用的名字。

推荐命名：

- `FrontendStateSnapshot`
- 或 `AgentBodyStateSnapshot`

当前可复用结构如下。

## 9.1 `FrontendStateSnapshot`

```ts
interface FrontendStateSnapshot {
  source?: string
  timestamp: string
  left: number
  top: number
  right?: number
  bottom?: number
  zoom_ratio: number
  display_name?: string | null
  display_type?: string | null
  display_animat?: string | null
  mode?: string | null
  working_state?: string | null
  work_name?: string | null
  work_type?: string | null
  bubble_visible?: boolean
  last_event_type?: string | null
  last_event_id?: string | null
  last_sequence_name?: string | null
  last_step_index?: number | null
  last_event_at?: string | null
}
```

字段解释：

- `left / top / right / bottom`: 当前空间位置或边界
- `zoom_ratio`: 当前缩放比
- `display_name`: 当前显示资源名
- `display_type`: 当前显示类型
- `display_animat`: 当前动画阶段
- `mode`: 当前模式
- `working_state`: 当前工作状态
- `work_name / work_type`: 当前动作或任务名
- `bubble_visible`: 气泡是否还在显示
- `last_event_type`: 最近消费的事件类型
- `last_event_id`: 最近消费的事件 ID
- `last_sequence_name`: 最近消费事件所属 sequence
- `last_step_index`: 最近消费的步骤号
- `last_event_at`: 最近消费事件时间

作用：

- 让后端知道前端现在的真实状态
- 让编排器做下一步门控判断
- 让调试页面观测执行结果

## 9.2 `FrontendStateResponse`

```ts
interface FrontendStateResponse {
  status: 'ok'
  state: FrontendStateSnapshot | null
}
```

作用：

- 包装状态查询结果
- 包装状态上报返回结果

## 10. 当前这套消息“可以做到什么”

如果另一个项目复用这套结构，理论上可以做到这些能力。

### 10.1 基础聊天前端

通过：

- `ChatRequest`
- `ChatResponse`
- `bubble.show`

可以做：

- 文本聊天
- 角色回复
- 聊天气泡

### 10.2 动作型前端

通过：

- `motion.play`
- `emotion.set`
- `mode.switch`

可以做：

- 表情切换
- 动作触发
- 模式切换
- UI 状态切换

### 10.3 位移型前端

通过：

- `window.move`
- `move.intent`

可以做：

- 窗口移动
- 角色走位
- 容器位移
- 靠边 / 归位

### 10.4 编排型前端

通过：

- `DevSequenceRequest`
- `wait_for`
- `settle_ms`

可以做：

- 小剧情脚本
- 分步演示脚本
- 状态驱动的连续行为
- 更复杂的角色表现

### 10.5 可观测前端

通过：

- `FrontendStateSnapshot`

可以做：

- 执行确认
- 错误排查
- 调试面板
- 后端闭环控制

## 11. 建议保留的最小通用子集

如果你想先在另一个项目里轻量落地，建议先只搬这组最小子集。

### 11.1 必选

- `ChatMessage`
- `ChatRequest`
- `ChatResponse`
- `BaseEventMeta`
- `bubble.show`
- `motion.play`
- `mode.switch`
- `window.move`
- `FrontendStateSnapshot`

### 11.2 第二阶段再加

- `emotion.set`
- `move.intent`
- `MemoryRecord`
- `MemoryRecallItem`
- `DevSequenceRequest`
- `DevSequenceStepRequest`
- `DevSequenceDispatchResponse`

## 12. 命名迁移建议

如果你要把它搬到另一个项目，推荐这样处理：

- 保留事件 `type` 不变
- 把 `VPetStateSnapshot` 重命名为 `FrontendStateSnapshot`
- 把 `PetEvent` 重命名为 `FrontendBehaviorEvent`
- 把 `DevSequenceRequest` 改成更正式的 `BehaviorSequenceRequest` 也可以

建议：

- 事件名尽量别改
- 类型名可以按项目改

因为真正跨项目兼容的是 payload 语义，不是类名本身。

## 13. 推荐的接口映射

如果另一个项目也想快速落地，推荐按下面这组接口组织。

- `POST /api/chat`
- `GET /api/events` 或 `GET /events/next`
- `POST /frontend/state`
- `GET /api/dev/state`
- `POST /api/dev/messages`
- `POST /api/dev/sequences`
- `GET /api/dev/scenarios`

但再次强调：

- 这些接口路径只是推荐
- 真正可复用的是消息体结构

## 14. 一句话结论

如果你要把当前项目的“后端驱动前端”能力拆成一个通用协议，最应该复用的就是这五组结构：

- 聊天消息
- 记忆结构
- 行为事件
- 编排结构
- 状态回传

其中最核心的是这条主线：

**后端发送 `FrontendBehaviorEvent`，前端执行并回传 `FrontendStateSnapshot`，复杂流程通过 `Sequence` 结构编排。**
