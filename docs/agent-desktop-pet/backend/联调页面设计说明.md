# 联调页面设计说明

## 1. 文档目的

本文档专门说明两个开发联调页面的设计：

- `http://127.0.0.1:18787/dev/control`
- `http://127.0.0.1:18787/dev/quick-test`

重点回答两个问题：

- 这两个页面分别是怎么设计的
- 它们为什么要存在，而且为什么要同时存在

这份说明基于当前代码实现整理，不是理想化设计稿。

## 2. 总体定位

这两个页面都不是正式业务页面，它们都属于“后端协议联调工具”。

共同目标：

- 验证后端发送给前端 / VPet 的消息协议是否成立
- 验证前端 / VPet 是否真的执行了对应行为
- 验证状态回传和 sequence 门控是否可用

但两者分工不同：

- `/dev/control`：偏“手工试验台”
- `/dev/quick-test`：偏“测试样例回放台”

## 3. 为什么需要这两个页面

当前系统不是简单聊天系统，而是“后端驱动身体层”的结构。

这意味着开发时会遇到几个问题：

- 不是每次都想从真实业务入口触发动作
- 不是每次都想手写 HTTP 请求
- 不是每次都想在前端页面里临时写按钮
- 不是每次都方便靠聊天文案间接触发表情、动作、移动

所以需要一套低成本联调入口。

### 3.1 为什么需要 `/dev/control`

因为开发阶段需要一个“可以随手造单条事件、试参数、看状态”的页面。

它解决的是：

- 某个事件类型能不能通
- 某个 motion / mode / graph 参数是否有效
- `window.move` 的位移量是否合理
- sequence 的门控参数是否合理

### 3.2 为什么需要 `/dev/quick-test`

因为当协议逐渐稳定后，仅靠手工表单已经不够了。

还需要：

- 保存一批固定测试样例
- 下次一键重放
- 把“你真正关心的测试集”沉淀成 JSON
- 给每个测试项记录通过 / 失败 / 现象说明

它解决的是：

- 回归测试
- 长链路测试复现
- 更贴近未来真实后端调用面
- 让测试项本身也可版本化

## 4. `/dev/control` 的设计

## 4.1 页面定位

`/dev/control` 是完整联调页。

它强调：

- 可视化表单
- 手工发单事件
- 手工触发预设场景
- 手工编辑自定义 sequence
- 实时观察状态回传

所以它本质上是一个“小型协议实验台”。

## 4.2 页面结构

页面主要分成四块。

### 4.2.1 顶部入口区

内容：

- 跳转到 `/dev/quick-test` 的链接
- 页面标题
- 对页面用途的简短说明

设计目的：

- 明确告诉使用者：这里是联调页，不是正式页面
- 明确告诉使用者：第一阶段主协议是 `window.move`
- 把更轻量的 Quick Test 页作为下一层工具入口

### 4.2.2 单事件发送表单

内容：

- 事件类型选择器
- 按事件类型动态切换可见字段
- `Send` 按钮

当前支持的可选事件类型：

- `bubble.show`
- `emotion.set`
- `motion.play`
- `mode.switch`
- `window.move`

表单字段按类型动态显示，例如：

- `bubble.show` 显示 `text`、`duration_ms`、`bubble.motion`、`emotion`、`graph`
- `motion.play` 显示 `motion`、`priority`
- `mode.switch` 显示 `mode`
- `window.move` 显示 `dx`、`dy`

设计目的：

- 不让用户一次面对所有字段
- 不让无关字段干扰当前测试
- 把“正式事件协议”直接可视化

### 4.2.3 组合场景区

内容：

- `组合场景` 标题
- 从 `GET /api/dev/scenarios` 拉取的预设 scenario 按钮列表

设计目的：

- 让常用组合行为可以一键触发
- 不再让前端页面自己保存组合步骤和延迟
- 把“组合行为编排”下沉到后端 sequence/scenario 层

也就是说，这一块体现的设计思想是：

**页面只负责触发，真正的步骤编排由后端统一管理。**

### 4.2.4 自定义 Sequence 区

内容：

- 一个 JSON 编辑框
- 一个 `Run Sequence` 按钮

默认内容就是一段较长的 6 步 sequence。

设计目的：

- 允许开发者直接测试长链路
- 允许快速试验 `delay_ms`
- 允许快速试验 `wait_for`
- 允许验证重复事件类型下 `event_id / sequence_name / step_index` 是否够用

这是 `/dev/control` 最“工程化”的部分，因为它已经不是单条事件调试，而是编排调试。

### 4.2.5 最新状态回传区

内容：

- 周期性调用 `/api/dev/state`
- 以 JSON 形式展示当前最新状态

设计目的：

- 看 VPet 是否真的消费了事件
- 看位置、动作、气泡是否按预期变化
- 看 sequence 是否真的走到了下一步

没有这块，联调就会退化成“我好像看到了”式主观判断。

## 4.3 `/dev/control` 的交互逻辑

核心流程是：

1. 手工选择事件类型或填写 sequence
2. 点击发送
3. 后端把请求转成正式事件或 sequence
4. 事件发布到 `EventBus`
5. VPet 插件轮询并执行
6. VPet 状态回传到后端
7. 页面继续刷新状态区

所以它实际上覆盖了整条最小闭环：

- 发消息
- 执行消息
- 回传状态
- 人工观察

## 4.4 `/dev/control` 解决的问题

它更适合解决这类问题：

- 某个事件字段到底应该怎么填
- 单条动作是否正常
- 某个 graph / motion 是否稳定
- 某个 sequence 的等待参数是否合理
- 状态回传字段是否够用

它不适合做的事情：

- 管理大量固定测试样例
- 记录每个测试项结果
- 承担长期回归测试入口

## 5. `/dev/quick-test` 的设计

## 5.1 页面定位

`/dev/quick-test` 是更轻量的测试目录页。

它强调：

- 从 JSON 文件读取测试项
- 点击某个测试项直接发送
- 支持单事件和 sequence 两种 payload
- 支持保存测试结果

一句话说：

**它是把“联调输入”从表单变成了可沉淀的 JSON 测试目录。**

## 5.2 页面结构

页面主要分成五块。

### 5.2.1 顶部导航和说明区

内容：

- 返回 `/dev/control` 的链接
- 页面标题
- 对 Quick Test 页定位的说明

说明里直接写清了：

- 这个页面比 `/dev/control` 更轻
- 它只做一件事：读取一份测试 JSON，然后点一个就发
- 如果 `payload` 是单事件，就发 `/api/dev/messages`
- 如果 `payload` 含有 `steps`，就发 `/api/dev/sequences`

设计目的：

- 把页面职责压缩到最小
- 避免再做一套重表单

### 5.2.2 测试目录编辑器

内容：

- 一个大文本框 `catalog-editor`
- 默认展示一份 JSON 目录

目录结构核心是：

```json
{
  "tests": [
    {
      "id": "move-right",
      "title": "右移 120",
      "description": "验证显式位移是否稳定。",
      "payload": {
        "type": "window.move",
        "dx": 120,
        "dy": 0
      }
    }
  ]
}
```

设计目的：

- 让测试项成为数据，而不是写死在页面逻辑里
- 让测试项可以存盘、复用、版本化

### 5.2.3 工具栏

当前按钮：

- `Load File`
- `Save File`
- `Load Tests`
- `Refresh State`

设计目的：

- `Load File`：从后端读取 `quick-tests.json`
- `Save File`：把当前编辑器内容写回文件
- `Load Tests`：把当前编辑器 JSON 渲染成卡片
- `Refresh State`：手工刷新状态回传

这让页面具备了最小“测试目录编辑器”能力。

### 5.2.4 测试卡片区

内容：

- 按卡片展示每个测试项
- 显示标题、描述、类型元信息、结果摘要
- 每个卡片有 `Run` 按钮

卡片会区分：

- 单事件：`event · xxx`
- 序列：`sequence · N steps`

设计目的：

- 让测试目录变成可点击的执行面板
- 一眼看出这是单事件还是 sequence
- 一眼看出是否已有测试结果

### 5.2.5 测试结果编辑区

内容：

- 当前测试名称
- 当前测试目标 / 描述
- 结果状态下拉框
- 结果说明文本框
- `Reload Result`
- `Save Result`

结果状态支持：

- `untested`
- `pass`
- `fail`
- `mixed`

设计目的：

- 不只是“能发”
- 还要把“这次发完看到什么”记录下来
- 让测试目录逐渐沉淀成验证资产

### 5.2.6 最近一次发送结果区

内容：

- 展示最近一次调用的 endpoint、结果和 payload

设计目的：

- 方便核对实际发了什么
- 方便排查“是不是页面组包错了”

### 5.2.7 最新状态回传区

内容：

- 和 `/dev/control` 一样，显示 `/api/dev/state` 的最新结果

设计目的：

- 让测试执行结果可被观察
- 让页面不是纯“发命令”，而是仍然保留最小闭环

## 5.3 `/dev/quick-test` 的核心设计思想

这个页面最关键的设计不是 UI，而是这三个点。

### 5.3.1 测试项从页面代码外移到 JSON

文件位置：

- `.explore/desktop-pet-vpet-body-bridge/quick-tests.json`

意义：

- 测试样例不再散落在页面源码里
- 更贴近未来真实后端会发的 payload
- 更容易扩充和沉淀

### 5.3.2 单事件和 sequence 复用同一个页面

页面通过判断 `payload.steps` 是否存在，自动决定：

- 单事件走 `/api/dev/messages`
- 序列走 `/api/dev/sequences`

意义：

- 不需要两套工具
- 保持测试入口统一

### 5.3.3 测试结果也写回同一份目录

测试项不仅有 `payload`，还可以附带：

- `goal`
- `result.status`
- `result.note`
- `result.updated_at`

意义：

- 测试目录从“可执行样例”升级为“带结果记录的验证资产”

## 5.4 `/dev/quick-test` 解决的问题

它更适合解决这类问题：

- 我想保留一批固定测试样例
- 我想下次一键重放
- 我想把当前协议样例沉淀下来
- 我想知道哪些测试已经通过、哪些还没过
- 我想让测试项更接近未来真实业务后端发出的 JSON

它不适合做的事情：

- 手工探索单个字段的所有可能组合
- 频繁改参数做即时试错

这些更适合 `/dev/control`。

## 6. 为什么不是只留一个页面

因为两个页面服务的是两种不同工作流。

### 6.1 `/dev/control` 对应“探索式联调”

特征：

- 先试一试
- 改参数
- 看效果
- 再改

适合：

- 协议还没完全收口
- motion / graph / dx / dy 还在试
- sequence 等待条件还在试

### 6.2 `/dev/quick-test` 对应“样例式验证”

特征：

- 先定义样例
- 一键重放
- 记录结果

适合：

- 协议已初步收口
- 开始做回归验证
- 想沉淀真实调用样例

如果只保留 `/dev/control`：

- 容易一直停留在手工点表单阶段
- 难以积累测试资产

如果只保留 `/dev/quick-test`：

- 初期探索成本太高
- 每次试小参数都要改 JSON

所以两个页面并存是合理的。

## 7. 这两个页面在整体架构中的作用

它们不是业务功能，而是“协议开发基础设施”。

在当前架构里，它们承担的是：

- 后端协议验证入口
- 前端 / VPet 执行观察入口
- sequence 能力验证入口
- 状态回传字段验证入口
- 测试样例沉淀入口

也可以理解成：

- `/dev/control` 让协议能被快速发明和试出来
- `/dev/quick-test` 让协议能被沉淀、重放和复验

## 8. 可迁移结论

如果你把当前“后端驱动前端”的方案迁移到别的项目，建议这两个页面的思路也一起迁移。

推荐直接保留两类工具页：

- 一个“全量手工联调页”
- 一个“基于 JSON 测试目录的快速回放页”

原因很简单：

- 前者适合探索
- 后者适合沉淀

这比只靠命令行或只靠正式业务页面调协议要稳定得多。

## 9. 一句话结论

`/dev/control` 是“协议实验台”，重点是手工造事件、手工造 sequence、实时看状态。

`/dev/quick-test` 是“测试样例回放台”，重点是把事件和 sequence 沉淀成 JSON 目录，一键执行并记录结果。

它们存在的原因不是为了做页面功能，而是为了把“后端驱动前端”的协议开发、验证、回归测试这三件事分层做好。
