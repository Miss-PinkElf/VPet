# 桌宠技术路线探索总结

更新时间：2026-03-25

## 1. 背景与问题来源

这次探索的起点，是在查看 `VPet` 仓库和“桌宠模拟器”方向后，发现 `VPet` 的整体展示效果、桌宠感和交互表现明显更强，因此开始怀疑当前项目选择 `Live2D` 是否合适。

当前项目的目标并不是单纯做一个传统桌宠模拟器，而是做一个具备以下特征的 AI 桌宠：

- 有持续陪伴感
- 有对话能力
- 有记忆能力
- 有低风险上下文感知能力
- 有明显的角色存在感和展示效果

这与已有 PRD 的定位一致，项目重点是“AI 陪伴型桌宠”，而不是纯养成型或纯动作型桌宠。

## 2. 为什么会产生“想换”的想法

产生换路线或换技术栈的想法，主要有以下几个原因：

### 2.1 `VPet` 的展示效果更强

`VPet` 看起来更像“真正的桌宠”，原因不是单一的模型技术，而是综合体验更成熟，包括：

- 动作反馈更强
- 状态切换更自然
- 桌宠行为更明显
- 窗口交互更有存在感

这会直接带来视觉落差，让人怀疑当前 `Live2D` 方案是不是不适合做桌宠。

### 2.2 当前 `Live2D` 模型资源不确定

当前项目虽然已经接入 `Live2D` 渲染链，但模型资源本身可能存在这些问题：

- 表情不够多
- 动作不够多
- 参数绑定不完整
- 不支持复杂姿态和夸张动作

这意味着后续如果要补“待机、说话、思考、关注、提醒、贴边、挂窗”等效果，可能会受到模型资产本身的限制。

### 2.3 对毕设节奏的担忧

如果继续把主线完全押在 `Live2D` 上，可能会出现以下风险：

- 花大量时间找模型
- 花大量时间适配模型
- 发现关键动作做不出来
- 最后只能展示“一个会说话的模型”，而不是“一个活的桌宠”

因此会自然地去考虑其他路径，例如：

- 改成动画方案
- 换成更适合桌面窗口行为的 `C# / WPF`
- 直接修改 `VPet` 源码，保留展示层，替换后端

## 3. 这次探索实际澄清了什么

这次讨论后，核心认知发生了变化：

> 问题不完全是 `Live2D` 对不对，而是“桌宠感”主要来自行为系统，而不只是渲染技术。

也就是说，`VPet` 的强观感并不只是因为它用了某种更高级的角色技术，而是因为它有：

- 状态机
- 窗口行为设计
- 动画资源矩阵
- 明确的交互节奏

这几个部分叠加起来，才让它看起来像桌宠。

因此，当前项目真正缺的，不只是模型，而是：

- 角色状态设计
- 展示层行为系统
- 窗口交互反馈
- 节奏编排能力

## 4. 探索过的几条路线

## 4.1 继续当前路线：`Electron + React + Live2D + Python`

这是当前仓库已经在走的技术路线。

优点：

- 与现有 PRD 完全一致
- 已经有前端雏形和 `Live2D` 渲染链
- 与 AI 对话、记忆、后端服务的结合自然
- 更符合“AI 陪伴型角色”的最终目标

缺点：

- 强依赖 `Live2D` 模型资产质量
- 大动作、夸张动作、挂边挂窗不如帧动画自然
- 如果角色资源不足，展示层容易受限

判断：

- 路线本身没有错
- 更适合长期目标
- 问题不在于“要不要废弃”，而在于要不要把角色表现层做成可替换

难度评估：中

## 4.2 临时改成动画方案

这里的“动画方案”主要指：

- `GIF`
- `WebP`
- `APNG`
- 序列帧动画
- 小型角色视频循环

优点：

- 临时出效果很快
- 不依赖复杂模型参数
- 更容易做“明显有动作”的桌宠
- 更适合快速做答辩展示占位

缺点：

- 状态切换细腻度不如 `Live2D`
- 角色很难像 `Live2D` 一样自然地“活着”
- 多状态下素材管理仍然不轻
- 如果直接拿 AI 生视频做正式素材，可控性较差

判断：

- 非常适合做兜底方案或过渡方案
- 不建议直接升格为长期主线，除非明确放弃 `Live2D`

难度评估：中低

## 4.3 半路转 `C# / WPF`

这样做的动机，是希望更接近 `VPet` 那类 Windows 桌宠的技术形态。

优点：

- 更适合做原生 Windows 窗口行为
- 桌宠吸附、置顶、边缘行为更贴近平台
- 如果目标是传统桌宠，`C# / WPF` 很合理

缺点：

- 需要重写前端壳层
- 要重新组织与 Python 后端的通信
- 当前已有 React/Electron 代码积累会大幅贬值
- 对毕设节奏风险很高

判断：

- 技术上可行
- 但现阶段不推荐
- 这属于重构项目路线，不是小优化

难度评估：高

## 4.4 修改 `VPet` 源码，保留展示层，替换后端

这是探索中最有诱惑的一条路线，因为看起来像是“直接复用成熟展示效果”。

优点：

- 可以快速继承成熟桌宠风格
- 窗口行为和展示感有现成参考

缺点：

- `VPet` 不是当前项目这种前后端分层架构
- 展示逻辑和核心逻辑并不一定能低成本拆开
- 改造成“前端展示层 + 自己的 AI 后端”并不轻松
- 代码许可和动画资源许可不是一回事，资源使用要额外注意

判断：

- 法律上代码可改，但资源使用要谨慎
- 工程上代价偏大
- 不适合作为当前主仓库的底座
- 但如果目标是单独开分支做“有限拆解 + 外部事件桥接”验证，这条路仍然值得探索

难度评估：中高

## 5. `VPet` 动画体系与 `Live2D` 的差异

根据 `VPet` 仓库公开说明，`VPet` 原生更偏向图片帧动画体系，而不是 `Live2D`。

这意味着它的优势更偏这些方面：

- 动作种类多
- 行为可设计得更夸张
- 更容易实现桌宠味很强的演出
- 对爬边、挂边、拖拽、特殊姿态更友好

而 `Live2D` 更擅长的是：

- 呼吸感
- 轻微视线变化
- 眨眼
- 嘴型联动
- 轻量表情变化
- “像一个角色在回应你”的感觉

因此两者并不是谁绝对更强，而是偏重点不同：

- `VPet` 风格更偏“像桌宠”
- `Live2D` 风格更偏“像角色”

## 6. `Live2D` 的主要缺陷

如果目标是最终展示效果尽量接近 `VPet`，那么 `Live2D` 的主要缺陷在于：

### 6.1 大动作不自然

例如：

- 爬墙
- 挂边
- 被提起
- 大幅摆动
- 夸张姿态切换

这些效果用帧动画更直接，用 `Live2D` 通常更受模型结构限制。

### 6.2 强依赖模型资产

你能做什么，不只取决于代码，更取决于模型是否具备：

- 对应表情参数
- 对应 motion
- 对应绑定关系

如果模型资产不够，后续很容易被卡住。

### 6.3 复杂状态扩展成本高

帧动画缺动作，可以补一组图。

`Live2D` 缺动作时，往往不是简单补图就行，而是要改模型本身，这对当前项目不友好。

## 7. 动画替换方案的成本判断

如果只把当前角色渲染层临时替换成动画组件，而不推翻整个桌宠壳层，那么成本并不高。

主要原因是：

- 当前外层前端已经在管理窗口、聊天和交互状态
- `Live2D` 渲染层相对独立
- 可以把“角色表现层”替换成序列帧或动画播放器

因此：

- 如果只做待机、说话、思考、提醒 4 个状态，成本中低
- 如果再补贴边反馈、拖拽反馈和过渡效果，成本会上升到中
- 如果想完全做出 `VPet` 那种丰富程度，成本会进一步上升到中高

## 8. 能不能用 AI 生图来做动画

可以，但要明确用途边界。

比较可行的方式有三类：

### 8.1 AI 生成角色图，再手工整理成状态图

这是当前最稳的方案。

适合：

- 做占位角色
- 做答辩展示
- 快速补待机、说话、思考等状态

优点：

- 可控
- 容易接入前端
- 与当前项目兼容性高

### 8.2 AI 驱动单图生成轻微动态

例如用单图驱动眨眼、张嘴、点头等。

适合：

- 做轻度动态头像或角色
- 做轻量说话反馈

但不适合：

- 大量复杂动作
- 明显桌宠式肢体行为

### 8.3 直接用 AI 生视频做桌宠动作

可以用于：

- 快速做演示素材
- 验证角色观感

不适合直接当长期正式素材，原因通常包括：

- 一致性不稳定
- 状态之间难以严格对齐
- 循环播放难以控制
- 透明背景和资源管理不方便

## 9. 为什么最终没有建议立刻“换”

这次探索后，没有得出“应该立刻换主栈”的结论，原因是：

### 9.1 当前路线并没有错

当前项目的目标是 AI 陪伴桌宠，而不是传统桌宠模拟器。

从目标匹配上看，当前路线依然成立。

### 9.2 现有代码已经有积累

当前仓库已经有：

- Electron 前端壳层
- React 交互层
- `Live2D` 渲染层
- 与 Python 后端联动的基础结构

如果现在推倒重来，损失明显大于收益。

### 9.3 真正缺的是行为系统，不是单纯换引擎

如果不补以下能力，即便换了技术栈，也未必自动变成优秀桌宠：

- 状态机
- 表情映射
- 窗口行为
- 节奏设计

## 10. 当前最稳的技术判断

结合当前项目阶段、已有代码和毕设节奏，最稳的判断如下：

### 10.1 主线不建议换

继续保留当前主线：

- `Electron`
- `React`
- `Python`

### 10.2 `Live2D` 可以保留，但不要绑死

应把角色渲染层设计为可替换：

- 现在可继续使用 `Live2D`
- 如果模型资源不够，可临时切到动画方案
- 后续如果找到更好的模型，再切回 `Live2D`

### 10.3 动画方案适合作为兜底

动画方案不是不能做，而是更适合：

- 临时占位
- 答辩演示
- 风险兜底

### 10.4 不建议现阶段迁到 `C#`

除非项目目标彻底转向“传统 Windows 桌宠模拟器”，否则当前不值得为此重构。

### 10.5 不建议把 `VPet` 当主项目底座

可以参考它的交互思路，但不建议把主仓库迁过去改。

## 11. 最终结论

一句话总结：

这次产生“想换”的原因，不是因为当前路线完全错误，而是因为 `VPet` 让项目看到了更强的“桌宠感”上限，而当前实现还停留在“模型显示层”。经过探索后，结论不是应该立刻换主栈，而是应该优先把角色表现层做成可替换，并把精力集中到状态机、窗口行为和交互节奏上。

当前建议如下：

- 主线继续保留现有技术路线
- `Live2D` 保留，但不强绑定
- 动画方案作为兜底和占位
- 不建议现在转 `C#`
- 不建议现在把主仓库迁到 `VPet` 源码上改

## 13. 本轮补充探索结论

这轮继续围绕“桌宠前端底座该怎么选”做了补充探索，重点不再是单纯比较观感，而是从以下几个角度判断：

- 是否已有开源底座可直接二次开发
- 现有 `Electron` 路线是否真的有明显问题
- 是否值得半路转 `C#`
- `Live2D` 与不同技术路线的兼容性如何

本轮新增的核心结论是：

> 当前阶段真正要优化的，依然不是“立刻换语言”，而是“选择一个足够稳的展示层底座，并尽快把后端行为决策与前端表现执行拆开”。

## 14. 开源桌宠前端底座补充判断

### 14.1 `WindowPet`

`WindowPet` 是目前看下来，最接近“可直接改成前端壳层”的开源项目之一。

优点：

- 开源协议较宽松，适合二次开发
- 技术栈接近现代前端工程形态
- 已经具备桌宠窗口壳层能力，例如拖拽、宠物管理、设置项、点击穿透等
- 更容易改造成“前端身体层 + Python 后端大脑”的结构

缺点：

- 当前更像多宠物覆盖层，而不是 AI 陪伴桌宠
- 角色表现能力偏轻，更多依赖帧动画和状态切换
- 如果目标是强 3D 观感，它本身上限不如 `Unity` 路线

判断：

- 如果目标是“尽快找一个前端壳层，自己专注 Python 后端”，它比从零写更现实
- 它适合作为“工程底座”，不一定适合作为“最终观感上限”

### 14.2 `Mate-Engine`

`Mate-Engine` 的价值不在于“省开发”，而在于“展示效果强、3D 表现上限高”。

本轮查看后可以确认，它不只是资源展示器，而是已经有较多“身体层”脚本，例如：

- 动画接收器
- 气泡处理器
- 移动控制器
- 角色对象接收器
- 内置 AI 相关绑定

这说明它理论上是可以改造成“后端驱动的桌宠前端”的。

但问题也很明显：

- 它是 `Unity` 项目，不是当前这种轻壳层模式
- 当前控制方式更多是 Unity 内部组件耦合，不是天然面向外部 Python 后端
- 如果要接现有后端，需要自己补一层桥接，例如 `WebSocket / HTTP / 本地消息协议`
- 许可证和默认资源分发要格外小心，不能简单当成 `MIT` 项目那样随意复用

判断：

- 可以作为“高表现展示分支”参考或二开对象
- 不适合作为当前主仓库的最低成本底座
- 如果未来要做“强展示答辩版”或 3D 强化版，可以重新评估

### 14.3 `BongoCat`、`Shimeji`、`PNGTuber` 方向

这几类项目也可以提供参考，但适合程度不同：

- `BongoCat` 更适合参考轻量桌面宠物壳层与自定义模型思路
- `Shimeji` 更适合参考传统桌宠行为模式，例如乱跑、贴边、挂边
- `PNGTuber` 类项目更偏直播形象驱动，不是天然的桌面 AI 陪伴系统

判断：

- 可以借鉴，不建议直接当主底座

### 14.4 `clawd-on-desk`

`clawd-on-desk` 的价值，在于它已经把“事件驱动桌宠身体层”做出了一个很轻的 `Electron` 版本。

本轮查看后可以确认，它不是单纯的静态挂件，而是已经具备了较完整的桌宠状态反应链，例如：

- 多状态动画切换
- 鼠标跟随
- 睡眠序列
- 多击反馈
- 任意状态拖拽
- 右边缘 mini mode
- 点击穿透
- 位置记忆

这说明它很接近当前项目最缺的那部分：不是 AI 能力本身，而是“事件到表现层状态”的映射能力。

但它的问题也很明确：

- 当前事件模型明显偏向 coding agent 会话，不是通用 AI 陪伴桌宠
- 角色资源形态是像素风 `SVG` 动画，不是 `Live2D`，也不是高自由度插画帧动画
- 它更像“事件反应宠物”，不是“自主行为宠物”
- 如果要接当前项目后端，需要把它的状态来源重写成自己的行为事件总线

判断：

- 很适合当“Electron 事件驱动桌宠身体层”参考项目
- 比 `AIRI` 更像桌宠，比纯静态壳层项目更接近状态机思路
- 不适合直接当主底座，但很适合拆解它的状态机、窗口交互和事件映射方式
- 如果当前探索重点是“怎样让桌宠真正动起来”，它值得作为 `WindowPet` 之外的重点参考对象

### 14.5 深度修改 `VPet` 的可行性补充

如果不把目标设成“整体重构 `VPet`”，而是改成“顺着现有结构做有限拆解”，那么这条路线的可行性会明显提高。

本轮进一步确认后，可以把 `VPet` 看成几层价值不同的结构：

- `Windows` 壳层与窗口行为
- `Graph / PNGAnimation / Picture` 一类表现层
- `MainLogic / GameCore` 一类内部行为逻辑
- 插件、资源、存档、工作流等产品化外围

其中真正值得保留和优先利用的，是前两层：

- 桌宠窗口行为
- 帧动画表现体系
- 现成的拖拽、贴边、提起、状态切换等桌宠感基础

而真正不适合一上来就重构的，是后两层：

- 现有内部行为逻辑耦合较深
- 许多机制是围绕原项目产品形态长出来的，不是为“外部 Python 大脑”设计的
- 资源许可与代码许可分离，发布时要额外小心

因此更现实的做法不是“把 `VPet` 改造成新的主项目底座”，而是：

- 单独开 `VPet` 探索分支
- 先保留原有桌宠壳层和表现层
- 再加一层外部事件桥，例如 `HTTP / WebSocket / Named Pipe`
- 让外部 Python 只发送高层行为事件
- 最后再把这些事件映射到 `VPet` 内部状态和动作

如果按实施顺序拆，这条路线更适合分三步：

1. 先打通“外部事件 -> `VPet` 动作状态”最小链路
2. 再隔离表现层接口，减少直接操作内部逻辑的范围
3. 最后才评估是否要继续动更深的行为逻辑

判断：

- 它不适合做当前主仓库底座
- 但适合做“高桌宠感方向”的独立拆解分支
- 它的价值不在于省开发，而在于直接借用成熟桌宠窗口行为和帧动画体系
- 如果探索目标是“能不能最快接近 `VPet` 那种桌宠味”，这条路线值得单独验证

## 15. 对现有 `Electron` 路线的补充判断

这轮讨论后，进一步确认了一个很重要的点：

`Electron` 不是“不能做桌宠”，而是“不适合做极致原生感的传统动作型桌宠”。

### 15.1 适合 `Electron` 做的部分

对于当前项目目标，`Electron` 很适合承担以下职责：

- 透明无边框窗口
- 置顶和基础窗口交互
- `Live2D` 或动画角色展示
- hover、toolbar、边框、缩放等交互壳层
- 聊天面板、气泡、设置页、日志页
- 与 Python 后端做 `IPC / WebSocket / HTTP` 联动
- 承担“前端身体层”的执行与仲裁逻辑

### 15.2 `Electron` 的真实局限

`Electron` 的主要局限，不在于聊天或 AI 联动，而在于桌宠味很强的原生窗口行为：

- 更复杂的窗口吸附
- 对任务栏或其他窗口的精细贴附
- 高性能复杂动作演出
- 透明命中区域与鼠标穿透的细节处理
- 多显示器、不同 DPI 下的原生窗口体验一致性

也就是说：

- 如果项目目标是“AI 陪伴桌宠”，`Electron` 仍然成立
- 如果项目目标是“传统桌宠模拟器”，`Electron` 会更吃力

### 15.3 这对当前项目意味着什么

对当前毕设而言，更合理的做法不是立刻抛弃 `Electron`，而是：

- 保留 `Electron + React + Python` 主线
- 把角色表现层做成可替换
- 把交互和状态执行层先做扎实
- 暂时不要过早追求极重的原生桌宠行为

## 16. 关于 `C#` 路线的补充判断

### 16.1 是否“好转”

如果这里说的“转 `C#`”是指整体前端主线改到 `C# / WPF` 或 `C# / Unity`，那么都不算“好转”。

原因是：

- 需要重写当前前端壳层
- 需要重做前后端通信桥
- 现有 `Electron + React` 的前端积累会明显贬值
- 毕设节奏风险会立刻上升

因此这不是“小优化”，而是“重构主路线”。

### 16.2 `C# / WPF`

`C# / WPF` 的优势主要在于：

- 更贴近 Windows 原生窗口控制
- 更适合传统桌宠的窗口吸附、原生行为
- 对 Windows 平台特性利用更顺手

但问题也很明显：

- 更像是在做原生桌面软件，不再是当前这种前端壳层模式
- 与现有前端代码体系断层较大
- 如果还想继续使用 `Live2D`，并不自然

判断：

- 技术上可行
- 现阶段不推荐

### 16.3 `C# / Unity`

如果目标是强展示效果，那么 `C# / Unity` 比 `C# / WPF` 更值得讨论。

原因：

- `Unity` 更适合角色展示、状态机和动画系统
- 与 `Live2D` 官方支持关系更直接
- 也方便未来切到 `VRM` 或 3D 模型路线

但缺点依然存在：

- 对当前项目来说仍然是换前端引擎
- UI、设置页、面板类开发体验一般不如 React
- 会把项目重心拉向展示层工程，而不是后端能力层

判断：

- 更适合做后续增强版或独立展示分支
- 不适合当前阶段直接替代主线

## 17. `Live2D` 与不同路线的兼容性补充

这轮进一步确认了一个容易混淆的问题：

- `Live2D + Unity` 是官方支持路线
- `Live2D + Web` 是官方支持路线
- `Live2D + Native` 是官方支持路线
- 但“`Live2D + WPF` 作为桌面 C# UI 路线”并不是当前最自然的官方主线

这意味着：

- 如果继续当前 `Electron` 路线，保留 `Live2D` 是合理的
- 如果未来真的要转 `C#`，更现实的 `Live2D` 搭配对象是 `Unity`，不是 `WPF`

## 18. 当前阶段更现实的表现层选择

结合前几轮探索，目前更现实的表现层排序如下：

### 18.1 第一优先级：继续 `Electron + Live2D`，但不要强绑定

适合：

- 当前主线推进
- 维持架构稳定
- 做“会陪伴、会对话、会反馈”的角色感

关键前提：

- 不要把 `Live2D` 当成唯一表现层
- 不要用它去硬扛所有大动作桌宠行为

### 18.2 第二优先级：准备动画/序列帧兜底方案

这条路线非常适合毕设风险控制。

适合：

- 快速补足待机、说话、提醒、思考等状态
- 做答辩展示兜底
- 在 `Live2D` 模型资源不够时快速替换表现层

### 18.3 第三优先级：将 `Unity` 视为强化展示分支，而不是现在的主线替代

适合：

- 后续做强展示版
- 尝试 3D/VRM 路线
- 做更像 `Mate-Engine` 的表现型桌宠

不适合：

- 当前阶段直接切主仓库

## 19. 本轮更新后的最终判断

经过这一轮补充探索后，当前最稳的结论进一步收敛为：

- 主线继续保留 `Electron + React + Python`
- `Live2D` 继续保留，但不强绑定
- 尽快把角色表现层设计成可替换结构
- 动画/序列帧方案应作为明确兜底
- `WindowPet` 更适合当“轻量壳层参考”
- `clawd-on-desk` 更适合当“事件驱动桌宠身体层参考”
- 深度修改 `VPet` 更适合当“高桌宠感拆解验证分支”
- `Mate-Engine` 更适合当“高表现展示分支参考”
- 当前不建议迁到 `C# / WPF`
- 当前也不建议为了观感焦虑而整体迁到 `Unity`

一句话概括本轮补充结论：

> 现阶段最重要的不是立刻换到 `C#`，而是先把“后端行为决策”和“前端表现执行”分层做好，并为角色表现层预留 `Live2D / 帧动画 / 后续 Unity` 的替换空间。
