# 桌宠项目交互控制设计稿

## 1. 文档目的

本文档基于当前讨论结果，以及以下两份已有文档整理而成：

- [桌宠项目详细PRD](./桌宠项目详细PRD.md)
- [原始PRD](../origin/原始PRD.md)

目标是把当前已经收敛出的核心需求、前因后果和推荐设计方式整理为一份可执行的中文设计稿，作为后续后端架构设计、前后端协议设计和实现拆分的依据。

## 2. 项目背景

桌宠项目的最初目标，不是做一个传统的 AI 工具入口，而是做一个具备长期陪伴感、人格连续性和逐步理解用户能力的桌面陪伴系统。

项目的外在表现形式是一个常驻桌面的 Live2D 桌宠，用户可以看到它、拖动它、与它对话。项目的内在能力则由 LLM、记忆系统、上下文感知、用户建模和行为决策共同组成。

从最开始的设想来看，项目希望实现以下体验：

- 桌宠常驻桌面，像一个真实存在的陪伴对象。
- 桌宠不是只在用户提问时响应，而是能逐渐理解用户习惯，并在合适的时候主动做出反应。
- 桌宠可以结合用户的电脑使用行为、时间习惯和历史互动，形成持续积累的记忆。
- 桌宠的行为应更像“一个人”，而不是一个冷冰冰的功能型程序。

随着项目推进，详细 PRD 对需求进行了收敛，明确了毕设阶段的约束：

- 优先保证 Windows 环境下可运行、可演示、可答辩。
- 高隐私能力默认关闭，不做激进监控。
- 前端负责桌宠展示、交互和窗口能力。
- 后端负责对话编排、记忆、感知、配置和能力模块。
- 前后端通过 IPC、WebSocket 或本地服务通信，由后端输出高层状态，前端负责具体表现。

## 3. 本轮讨论后明确的需求

在本轮讨论中，需求进一步明确为：

- 后端不仅负责对话和记忆，还需要具备控制前端表现的能力。
- 后端应能控制或决定桌宠的表情、动作、对话气泡文案和行为模式。
- 后端最好还能影响模型位置、大小、朝向、靠近鼠标、贴边等行为。
- 前端应尽量负责展示和本地交互，而不是承担复杂决策逻辑。
- 整体架构希望呈现为“后端像大脑，前端像身体”的模式。
- 系统需要一定的“社会学感”或“行为分析感”，让桌宠不是只回答问题，而是逐渐理解用户。

换句话说，当前真正要解决的问题不是“前后端要不要分开”，而是：

- 后端应该控制前端到什么程度。
- 前端哪些能力必须保留自主权。
- 前后端之间应该通过什么协议协作。
- 用户建模和行为分析应该如何在工程上落地。

## 4. 设计目标

本阶段推荐围绕以下目标设计：

- 建立清晰的前后端职责边界。
- 让后端具备高层行为决策能力。
- 让前端专注于渲染、交互和状态执行。
- 避免后端直接硬控前端底层属性导致冲突。
- 让协议可扩展，后续便于新增动作、表情和状态。
- 让 MVP 阶段即可支撑答辩演示和后续扩展。

## 5. 核心设计结论

推荐采用以下总体方案：

**后端做高层决策，前端做本地执行与仲裁。**

具体含义如下：

- 后端负责判断“为什么做”和“做什么”。
- 前端负责决定“怎么做”和“当前能不能做”。
- 前后端之间传递的是高层行为事件，而不是每一帧的底层渲染命令。
- 前端对拖拽、缩放、hover、动画冲突等强交互行为保留最终控制权。

这意味着，系统不能设计成“后端直接接管前端所有属性”，而应设计为“后端发送意图，前端执行意图”。

## 6. 推荐职责划分

### 6.1 前端职责

前端建议承担“身体和表情层”的职责：

- Live2D 模型渲染
- 表情与动作播放
- 对话气泡展示
- 对话面板 UI
- toolbar、hover、边框高亮
- 拖拽、缩放、贴边等本地窗口交互
- 本地动画过渡与状态维护
- 对后端指令进行冲突判断和执行仲裁

前端不建议承担长期记忆推理、用户习惯分析、行为策略判断等复杂业务逻辑。

### 6.2 后端职责

后端建议承担“大脑和中枢”的职责：

- 感知服务：采集活动窗口、应用名、时间段、使用时长等低风险上下文
- 记忆服务：管理工作记忆、事件记忆、语义记忆
- 对话编排器：整合用户输入、感知结果和记忆召回
- 用户模型服务：维护熟悉度、打扰容忍度、兴趣偏好、行为习惯等状态
- 行为策略引擎：决定当前是否说话、使用什么情绪、触发什么动作、是否主动提示
- 配置与隐私服务：管理权限开关、日志级别、演示模式
- 事件分发器：向前端发送行为事件

### 6.3 Electron 主进程职责

Electron 主进程建议承担桥接职责：

- 窗口生命周期管理
- IPC 通信
- 系统 API 接入
- 前后端消息中转
- 本地能力边界控制

## 7. 推荐控制边界

### 7.1 适合由后端控制的内容

以下内容适合由后端决定，再由前端执行：

- 当前情绪
- 当前动作意图
- 当前表情意图
- 对话气泡文字
- 主动提示频率
- 模式切换，例如安静模式、陪伴模式、提醒模式
- 是否触发某类行为事件

### 7.2 可由后端提出，但前端必须仲裁的内容

以下内容可以由后端提出意图，但不建议后端直接强行设置底层值：

- 模型位置变化
- 模型临时缩放
- 靠近鼠标
- 贴边停留
- 自动移动到某一区域
- 演示脚本中的定点移动

原因如下：

- 这些行为容易与拖拽、缩放等用户操作冲突。
- 这些行为容易与本地动画、边界限制和窗口状态冲突。
- 前端更了解当前是否允许执行这些动作。

### 7.3 应由前端主导的内容

以下内容建议完全由前端主导：

- 鼠标拖拽过程
- resize 过程
- hover 态
- toolbar 显隐
- Live2D 参数过渡细节
- 多个动作之间的平滑切换
- 窗口边界与安全区域控制

## 8. 推荐事件驱动设计

推荐通过统一事件协议，让后端向前端发送高层行为事件，而不是直接修改具体渲染属性。

第一阶段可以先定义五类核心事件：

- `emotion.set`
- `motion.play`
- `bubble.show`
- `mode.switch`
- `move.intent`

示例：

```json
{
  "type": "emotion.set",
  "emotion": "curious"
}
```

```json
{
  "type": "motion.play",
  "motion": "wave_slow",
  "priority": 80
}
```

```json
{
  "type": "bubble.show",
  "text": "你已经连续写代码两个小时了，要不要休息一下？",
  "duration_ms": 5000
}
```

```json
{
  "type": "mode.switch",
  "mode": "quiet_companion"
}
```

```json
{
  "type": "move.intent",
  "intent": "dock_right"
}
```

前端收到事件后的处理流程建议为：

1. 解析事件类型。
2. 判断是否与当前用户操作冲突。
3. 判断当前动作优先级是否允许被打断。
4. 决定立即执行、延迟执行或忽略执行。
5. 将高层事件翻译为具体的 Live2D 参数、动作和 UI 表现。

## 9. 推荐新增的关键模块

### 9.1 前端 `Pet Controller`

建议前端增加统一的桌宠控制层 `Pet Controller`，而不是让多个组件分别处理后端事件。

其职责包括：

- 接收后端行为事件
- 维护当前桌宠状态
- 管理动作队列和优先级
- 处理动画冲突
- 统一映射表情、动作、气泡和位移行为
- 协调拖拽、缩放、hover 等本地交互状态

这样可以避免前端控制逻辑散落在多个组件中，提升维护性。

### 9.2 后端 `behavior_policy_engine`

建议后端新增核心模块 `behavior_policy_engine`，作为桌宠行为决策中枢。

其输入建议包括：

- 当前活动应用
- 当前时间段
- 当前使用时长
- 最近互动行为
- 相关记忆召回结果
- 用户偏好与习惯标签
- 当前熟悉度和打扰容忍度

其输出建议包括：

- 是否说话
- 说什么
- 用什么情绪说
- 是否切换表情或动作
- 是否进入安静模式
- 是否发起移动意图

这个模块是系统中最接近“桌宠人格”和“社会学感”的部分。

## 10. 关于“社会学感”的推荐实现方式

当前不建议直接追求复杂的社会学理论建模，也不建议一开始就寻找所谓“社会学算法库”。

更适合 MVP 的方式是分三层实现：

### 10.1 统计层

- 统计什么时间使用什么应用
- 统计使用时长
- 统计互动频率
- 统计高频话题和兴趣标签

### 10.2 用户画像层

- 判断用户偏夜间活跃还是白天活跃
- 判断当前更接近专注、放松还是空闲状态
- 判断偏好的互动频率
- 识别常见行为模式

### 10.3 关系状态层

- 熟悉度
- 信任度
- 打扰容忍度
- 最近互动质量
- 当前亲近程度

这些能力在 MVP 阶段可以先使用以下工程方式实现：

- 规则
- 时间窗统计
- 标签累积
- 简单评分模型
- 有限状态机

例如：

- 连续多天深夜使用 VSCode 超过一定时长，标记“深夜 coding”习惯。
- 用户连续关闭提示气泡，降低主动打扰频率。
- 用户近期主动聊天次数上升，提高陪伴模式权重。

这样已经足以支撑“像在理解人”的体验雏形。

## 11. 推荐落地顺序

为降低复杂度，建议按以下顺序逐步实现：

1. 先定义前后端事件协议。
2. 设计前端 `Pet Controller`。
3. 设计后端 `behavior_policy_engine`。
4. 先打通“气泡 + 表情 + 动作”三件套。
5. 再加入模式切换。
6. 最后谨慎接入位置和大小意图控制。

推荐这样排序的原因是：

- 表情、动作和气泡是桌宠陪伴感最直观的外显层。
- 位置和大小控制更容易和拖拽、窗口交互冲突。
- 先完成低风险高收益链路，更适合毕设阶段演示和答辩。

## 12. 结论

当前最推荐的设计方向可以概括为：

- 前端不是大脑，前端是桌宠的身体和表情层。
- 后端不是简单接口层，后端是桌宠的感知、记忆和决策中枢。
- 前后端之间通过事件驱动协议协作，而不是让后端硬控所有底层属性。
- 用前端 `Pet Controller` 管理表现执行。
- 用后端 `behavior_policy_engine` 管理行为决策。
- 用轻量用户建模替代空泛的“社会学算法”概念。

这套方案既符合原始设想中“像一个人一样陪伴”的目标，也符合详细 PRD 中“模块解耦、可替换、可演示、可交付”的工程要求。
