# Proposal

## Summary

- Change name: `desktop-pet-companion-roadmap`
- Goal: 将桌宠项目从一份大而全的 PRD 拆解为可持续推进的 OpenSpec 工件，并按阶段规划实现顺序，优先保障毕业设计可交付，再逐步增强演示效果与长期扩展性。
- Why now: 当前目标、技术方向和功能边界已经明确，但单一 PRD 体量过大，不适合作为后续逐步实现的唯一上下文。需要把需求映射为稳定的 `proposal.md / design.md / tasks.md` 三件套，后续实现仅围绕原子任务推进。
- Current implementation delta: 前端展示、拖拽、缩放和 hover toolbar 已稳定。本轮将主线切换到“简单对话 + 后端最小闭环”：补齐统一启动入口、Python HTTP 服务、OpenAI 兼容 LLM 代理、前端文本输入、发送状态和桌宠气泡回复。

## Scope

- In scope:
  - 基于现有 PRD 输出一个面向实现的变更工作区。
  - 明确项目分阶段目标：`Phase 1 毕设 MVP`、`Phase 2 演示增强与架构可扩展`、`Phase 3 长期产品雏形`。
  - 将前端桌宠、对话、记忆、轻量上下文感知、启动与配置能力拆成独立可验证任务。
  - 为 Phase 1 新增最小后端对话服务：`FastAPI` 服务、健康检查接口、OpenAI 兼容 `/v1/chat/completions` 代理调用。
  - 固定前后端通信方式为本地 `HTTP`，并定义最小聊天请求/响应契约。
  - 在前端补齐最小文本对话入口：输入框、消息列表、发送中/成功/失败状态、桌宠气泡回复。
  - 提供一个仅用于联调的后端测试页，允许手动输入文本并把消息主动推送到前端桌宠。
  - 将后端重构为模块化结构，至少拆出配置层、API 路由层、对话编排层、事件分发层和低耦合记忆接口层。
  - 根目录提供统一启动入口，可同时启动 `frontend` 和 `backend`。
  - 为后续实现定义优先级、阶段边界、非目标和风险。
- Out of scope:
  - 本次不进入记忆抽取、上下文感知、语音、多模态或工具调用的代码实现。
  - 本次不处理 Electron 打包时的 Python 进程随包分发问题，先保证开发态联调稳定。
  - 本次不实现流式输出、打字机效果或多轮持久会话恢复。
  - 本次不实现复杂后台管理页面，只提供一个最小联调表单页。
  - 本次不强接真实 `mem0`，先完成可替换的记忆接口与占位实现。
  - 本次不确定最终 LLM 服务商、向量库、TTS/ASR 服务商的具体落地版本。
  - 本次不承诺 MVP 中实现摄像头、麦克风、屏幕分析、浏览器历史读取、自动执行任务等高风险能力。
  - toolbar 中除设置与缩放外的其他按钮，本次只定义展示与占位，不承诺接入真实业务功能。

## User Scenarios

- Primary flow:
  - 作为项目作者，我需要从杂乱需求中得到一套稳定工件，用来指导后续分阶段开发。
  - 作为后续执行者，我每次只需要读取当前 change workspace 下的三个文件，即可知道本阶段做什么、不做什么、先后顺序和验收标准。
  - 作为答辩准备者，我需要先交付一版稳定可演示的桌宠，而不是同时追求所有高级能力。
  - 作为桌宠用户，我希望鼠标移入后能看到与视觉稿一致的工具栏和操作边框，并能直接拖动或缩放桌宠，而不是通过额外面板完成。
  - 作为桌宠用户，我希望点击 toolbar 中的“对话”入口后，可以输入一句话并看到桌宠返回气泡回复，而不是只有静态模型。
- Important edge cases:
  - 如果某阶段实现暴露出设计耦合过深，需要可以回滚到 design 层修订，而不是继续堆功能。
  - 如果 Windows API、记忆中间件或模型接口选型变化，不应推翻整体路线图。
  - 如果毕业设计时间不足，必须可以只完成 Phase 1 仍然形成完整闭环。
  - 当鼠标短暂移出桌宠边缘时，边框与 toolbar 不应立即消失，避免用户无法命中拖拽点或按钮。
  - 当窗口持续缩放时，模型必须持续重新适配，而不是停留在旧比例导致裁切或留白。
- Failure or empty states:
  - LLM 不可用、密钥缺失或后端未启动时，桌宠 UI 仍应可展示，且前端能给出明确错误反馈。
  - 记忆模块暂未接入时，聊天功能应退化为无长期记忆模式。
  - 活动窗口感知失败时，不应阻断对话主链路。
  - toolbar 中未接业务的按钮应采用明确占位态，不能误导为已可用功能。

## Constraints

- Technical constraints:
  - 前端技术栈固定为 `Electron + React + Ant Design + Vite + TypeScript + CSS Modules`。
  - Live2D 需沿用当前已知稳定组合：`pixi.js@6` + `pixi-live2d-display@0.4.0`。
  - 项目采用前后端同仓结构，根目录保留统一启动脚本，后端采用 `Python` 并需要规范的虚拟环境与启动方式。
  - 后端第一版仅使用 `FastAPI + uvicorn + python-dotenv + 标准库 HTTP 客户端`，不引入 LangChain、记忆框架或额外编排层。
  - LLM 调用优先适配 OpenAI 兼容接口，模型默认优先 `gpt-5.4`，其次 `gpt-5.2`。
  - MVP 主平台优先 `Windows`，`macOS` 不作为本阶段稳定性交付目标。
- Product or design constraints:
  - 产品定位优先是“陪伴型桌宠”，不是通用效率工具。
  - 毕设阶段必须优先保证演示稳定和功能闭环，而不是追求拟人化上限。
  - 所有高敏感采集能力默认关闭，必须提供明确开关和边界说明。
  - 桌宠 hover 态的 toolbar 布局要尽量贴近视觉稿，保持右侧竖排、圆角浮层、右下角独立缩放手柄。

## Risks And Open Questions

- Risk 1: “像一个人一样”是抽象目标，如果不转成阶段性验收标准，任务会无限膨胀。
- Risk 2: 如果本轮直接把记忆、感知和聊天编排揉在一起，后续很难替换底层实现。
- Risk 2.1: 如果后端继续维持单文件入口，随着行为事件、记忆和配置增长，会很快失去可维护性。
- Risk 3: 若把模型密钥写入前端或仓库，会带来安全和答辩展示风险。
- Risk 4: 若前端直接耦合具体模型协议，后续切换供应商或引入记忆层会导致 UI 层返工。
- Open question 1: 开发态通信已固定为本地 HTTP，后续打包阶段是否继续保留 HTTP 还是迁移为主进程子进程桥，当前保留为 `TBD`。
- Open question 2: Phase 1 的聊天是否需要流式输出，当前明确为“不做”，后续再评估。
- Open question 3: 记忆模块 MVP 是否直接以 `mem0 + 本地存储` 起步，还是先做抽象接口 + 简化本地存储，当前仍待实现时确认。
